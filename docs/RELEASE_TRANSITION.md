# Переход beta5 в стабильную линию

Ограничения владельца: не удалять и не переименовывать старые ветки, не включать защиту `main`, не переписывать историю. Этот документ не подтверждает публикацию релиза.

## Целевое состояние

| Объект | Назначение |
| --- | --- |
| `main` после слияния | Стабильная линия `0.96.0`, исходный код beta5 |
| `dev/v0.97-beta1` | Разработка `0.97.0-beta1`, без публикации |
| `dev/v0.96-beta5` | Неизменённый источник стабильной версии |
| Остальные старые ветки | Исторические, остаются под прежними именами |
| `archive/...` | Дополнительные снимки исходных состояний, не новые релизы |
| Старые Releases | Сохраняются с исходными файлами; архивный статус отмечается в заголовке/описании |

Номер `0.96.0` выбран для существующего release workflow: он считает версии с alpha/beta/rc предварительными. Это правило проекта, не запрет GitHub: [API Release](https://docs.github.com/en/rest/releases/releases) определяет полный выпуск параметром `prerelease=false`. Название beta5 сохраняется как происхождение стабильного выпуска.

## Распределение действий

| Шаг | Исполнитель | Ограничение |
| --- | --- | --- |
| Подготовительная ветка из beta5 и номер 0.96.0 | Ассистент | QML и workflows не меняются |
| README, CHANGELOG, ROADMAP, история, этот план | Ассистент | Не заявлять о состоявшейся публикации |
| Новый PR в main и проверка CI | Ассистент | Без настройки защит |
| Номер 0.97.0-beta1 и описание разработки | Ассистент | Без тега и Release |
| Закрыть старый draft PR #11 как заменённый | Ассистент | Не удалять ветку и обсуждение |
| Проверить/выключить серверное автоудаление веток | Владелец, CLI | До merge подтвердить false |
| Резервный bundle и archive-теги | Владелец, CLI | В подключении нет создания тегов |
| Merge с проверкой HEAD и успешного package | Ассистент | После проверки автоудаления |
| Проверить виджет в своей Plasma | Владелец | Проверка сборки не заменяет GUI-тест |

| Пометить старые Releases как архивные | Владелец, CLI | Без замены assets и тегов |
| Итоговая проверка GitHub | Ассистент | Проверить опубликованный результат |

Административный доступ не добавляет отсутствующие операции подключения: для тегов и Release нужен CLI. Все CLI-блоки запускать в bash, не непосредственно в fish. Не присылать токены в чат.

## Проверка перед слиянием

```bash
REPO=aliksandrkarankevich-sudo/AI-PlasmaDriveCard
gh auth status
gh api "repos/$REPO" --jq '{default_branch,delete_branch_on_merge}'
```

Если `delete_branch_on_merge=true`, выключить только автоматическое удаление веток:

```bash
gh api --method PATCH "repos/$REPO" -F delete_branch_on_merge=false
```

Это не защита main и не ограничение push. Отсутствие `--delete-branch` в команде merge не отменяет серверную настройку автоудаления. До получения false PR не сливать.

## Порядок завершения

1. Сохранить refs и `git bundle --all` в отдельном временном клоне; не работать с незакоммиченными изменениями основной локальной копии.
2. До слияния создать `archive/main-before-v0.96.0`; дополнительные archive-теги привязать к точным SHA старых веток. Не создавать теги `v*` для архива, чтобы не запустить Release. Существующие теги не передвигать.
3. Подтвердить отключённое автоудаление веток и зелёную проверку `package` нового PR. Проверить неизменность исходной beta5.
4. Ассистент выполняет обычный merge нового PR с expected HEAD, без squash, force-push и удаления ветки. Если текущие SHA изменились, сначала повторить анализ.
5. Проверить кандидат в Plasma. Наличие номера stable не означает, что все незавершённые задачи закрыты.
6. Создать аннотированный `v0.96.0` на проверенном merge-коммите, убедившись, что номер metadata равен 0.96.0 и содержимое `package/contents` и `scripts` идентично исходной beta5.
7. Push только этого тега запускает существующий Release workflow. Дождаться успеха, наличия `.plasmoid` и `SHA256SUMS`; не создавать второй Release параллельно и не передвигать тег при ошибке.
8. Через CLI явно выставить `prerelease=false`, `make_latest=true`. Старым Releases добавить `[ARCHIVE]` и пояснение, сохранив исходное описание, файлы и теги.
9. Проверить `/releases/latest`, контрольные суммы, номер в архиве, наличие всех старых веток и рабочую 0.97-beta1.

Архивный статус — соглашение проекта, не блокировка отдельных веток. Не архивировать репозиторий целиком: это остановит разработку. Не включать защиту main.

## Независимость линий

После отдельного повышения версии в 0.97-beta1 не выполнять слепое merge main в неё: изменения metadata/документации могут конфликтовать. При переносе документации сохранять номер `0.97.0-beta1`, а исправления кода переносить осознанно. Автоматическая синхронизация веток в этот переход не входит.

## Откат

До merge подготовка отменяется закрытием нового PR; beta5 и main сохранены. После merge отмена — новый revert-коммит по фактическому merge SHA, не reset/force-push. После публикации исправления выпускать новым тегом, а не заменять файлы старого Release. Резервный bundle хранить до проверки результата.
